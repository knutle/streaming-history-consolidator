# Streaming history project lessons

- Treat exported archives and listening history as private. Inspect real exports locally only as needed; use synthetic fixtures in tests, and never commit or disclose personal records. Persist only the music and playback metadata needed by the application.
- Preserve per-user, per-source deduplication and existing fingerprints when changing import readers. Re-imports may enrich or match previously unmatched listens, but must not overwrite existing manual matches or mix users' data.
- Imports process each history file in a transaction. Cancellation rolls back the file in progress, while completed files remain imported. Keep progress reporting outside that write transaction and clearly distinguish provisional progress from committed results.
- Imports use a dedicated queue and private staged files. Run the web server and imports worker independently when testing responsiveness; the standalone worker is `php artisan queue:work imports --queue=imports --timeout=7200 --tries=1`. Do not force-abort stranded imports until all import workers and automatic restarts are stopped.
- Automatic matching uses the local MusicBrainz database and must not call external APIs. MusicBrainz API recording, artist and release searches and Spotify metadata lookup are explicit user actions; validate identifiers, use fixed API hosts, and keep credentials server-side. The MusicBrainz API throttle requires a cache shared by the app's web workers and instances.
- Confirming an artist match queues a scan on the imports worker. API scans are opt-in and send recording and album names to MusicBrainz; preserve existing matches, check the current artist association, and leave ambiguous recordings unmatched. Verified artist aliases are shared MusicBrainz metadata used as a fallback for later local matching.
- Support both the full MusicBrainz database and canonical SQLite data when changing matching. Canonical data has no explicit artist aliases or ISRCs, and a multi-artist credit does not identify individual artist names. Avoid guessing when matches or metadata joins are ambiguous.
- Canonical recording data includes release titles but not first-release dates, release artist credits, or release-group types. MusicBrainz search results may include only some related releases; label these limitations rather than presenting inferred or partial data as complete.
- Canonical multi-artist credits do not reveal individual names. Persist verified artist names returned by explicit API recording matches; a missing artist name may be looked up explicitly from its owner-authorized detail page without sending listen metadata.
- Shared MusicBrainz entities do not grant access to another user's listens: scope queries and changes to the authenticated user. Manual artist groups use the exact imported artist credit; album groups also include the exact album name. Manual MusicBrainz selections replace the relevant associations for the group and apply to future imports; removing a saved choice leaves existing associations unchanged.
- MusicBrainz editor links must not present catalog metadata as authoritative. Keep catalog evidence in the edit note and only prefill recording title and artist when the matched catalog titles agree; users must review the applicable MusicBrainz style guidelines.
- Linked catalog groups keep deduplicated references to the original catalog metadata per source member. Run `php artisan catalogs:refresh-linked-evidence` after deploying to backfill existing groups; it skips users with active imports.
- Matched native Apple and Spotify catalog items are automatically linked per user by exact recording MBID. Conflicting or manually excluded catalog items remain separate; unlinking excludes that item from future automatic links until it is explicitly linked again. Run `php artisan catalogs:link-matched` after deploying to backfill existing matches; it skips users with queued or active imports or artist scans. Unlinks made before automatic-link exclusions existed cannot be reconstructed, so review existing matches before running the backfill.
- MusicBrainz's artist editor accepts seeded GET parameters, but its release editor requires a multipart POST. Artist and album names from imports and manually saved catalog links are unverified evidence, not proof of canonical names or release details.
- Tests use isolated SQLite by default, while the application may use another database. Verify database-specific query and collation behavior on the relevant engine, and report when that engine or a migration is unavailable rather than assuming SQLite proves compatibility.
- Local Docker development uses Laravel Sail: `./vendor/bin/sail up -d`, `./vendor/bin/sail artisan migrate`, and `./vendor/bin/sail test`. The Compose stack uses MySQL, Redis, Mailpit, and Selenium; Mailpit only receives mail when the mailer is configured to use it.
- Sail's installer can modify `.env` and `phpunit.xml` and pull/build images. Inspect its effects before running it on an existing setup; preserve the SQLite test configuration unless a database change is explicitly intended. MySQL can expose differences such as JSON key ordering and aggregate result types.
- The default seeder creates a verified `test@example.com` user with the factory password `password`. Use it only for local development; it is not idempotent, so check for the user before seeding again and never reset an existing account without approval.
- Docker Desktop storage errors may reflect a read-only VM filesystem or low disk space. Diagnose first; do not restart Docker or prune images, build cache, containers, or volumes without considering other users and obtaining approval for disruptive or destructive actions.
